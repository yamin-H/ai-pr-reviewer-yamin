Section 01The project in three sentences

Short answers first, then the exact files, functions, and commits that support each one.

1 — What problem does it solve?
It removes manual first-pass PR review: when a pull request is opened or updated, it reads the diff, has an LLM flag bugs, security issues, and bad patterns, posts a native GitHub review on the exact changed lines, and learns from the team's approve/dismiss decisions so later reviews follow that team's conventions.
Evidence. README.md:11 describes an “autonomous, production-grade Pull Request Review engine”; README.md:85 promises native reviews with path, line, side annotations. In code, agent/app/services/github.py:93 post_pull_request_review() calls pr.create_review(commit, body, event, comments) at line 122, with an issue-comment fallback at line 137. The learning loop is agent/app/services/memory.py (store_decision(), search_memory()) against MemoryEntry with a vector(384) column (api/prisma/schema.prisma:94–107).
2 — Who is the intended user?
Engineering teams on GitHub, organised as an organization — developers and tech leads who install a GitHub App on the org's repositories and then use a dashboard to watch reviews and give feedback.
Evidence. Organization is the tenancy root in api/prisma/schema.prisma:12, with installationId, plan, monthlyReviewCount, and relations to users, repos, reviews, digests, and memory entries; every User carries an orgId (line 40). README.md:87 states “complete tenant isolation across organizations” and README.md:129 tells you to create the App in organization settings. Commit cac6b7d (“look up org login from GitHub API in installation callback”, 20 Jul 2026) is a fix that only matters when the organization is the unit of installation.
3 — What output does it produce?
Three deliverables: a native GitHub PR review (approve, comment, or request changes, with inline annotations), a live Next.js dashboard with SSE pipeline progress, review history and learned-convention memory, and a weekly digest plus monthly quota reset driven by cron.
Evidence. Review output: agent/app/graph/review/nodes/post_comments.py:11–30 selects APPROVE / REQUEST_CHANGES / COMMENT. Dashboard and streaming: api/src/routes/internal.ts:93 handlePipelineStream(), exposed at api/src/app.ts:106, with pages under frontend/src/app/dashboard/. Digest and quota: api/src/lib/cron.ts:34 startCronJobs() schedules Monday 09:00 ('0 9 * * 1', line 36) and the first of the month ('0 0 1 * *', line 45) via digestQueue (api/src/queues/digestQueue.ts).

1.2README versus code — say these carefully

Do not repeat the README's embedding claim

README.md:86 and :120 claim all-MiniLM-L6-v2. The code actually loads BAAI/bge-small-en-v1.5 in agent/app/services/embeddings.py:4, via fastembed. Both produce 384-dimensional vectors, which is why the schema column (vector(384)) is still correct. If asked which model, say bge-small and note the README is stale.

Other small mismatches

Memory scoping. The README says memories are scoped by orgId and repoId (README.md:121), but search_memory() filters only on repoId (agent/app/services/memory.py:90–92). The MemoryEntry row does store orgId, and writes are given it, but retrieval does not use it.

Frontend version. The README badge says Next.js 14 (README.md:3); frontend/package.json:19 pins Next 16.2.10.

No tests, CI config, or LICENSE file are present in the tree, despite README.md:9 linking to a license.

2.3Step by step

STEP 0

Trigger

GitHub → POST /webhooks/github  ·  api/src/routes/webhooks.ts

A developer opens a PR or pushes new commits to it. GitHub delivers a pull_request event (the App is subscribed to it, README.md:148) with header x-github-event: pull_request.

In: GitHub JSON payload (repository, pull_request, installation, organization, sender).  Out: HTTP request to the Node API.
STEP 1

Verify the signature

api/src/middleware/webhook.ts → verifyWebhookSignature()

Reads GITHUB_WEBHOOK_SECRET, computes sha256=HMAC(rawBody), and compares it against x-hub-signature-256 with crypto.timingSafeEqual (length checked first). Missing secret → 500; missing, malformed, or wrong signature → 401.

In: raw Buffer + signature header.  Out: next() or HTTP 401.
STEP 2

Route the event, apply guards, create the review row

api/src/routes/webhooks.ts → router.post('/github')

Parses JSON, then acts only on action === 'opened' || 'synchronize' (line 117). Guards run in this order:

  • Idempotency — Redis SET webhook:dedup:<repoId>:<pr>:<action>:<sha> NX EX 60 (line 130). Duplicate → 200 duplicate_webhook.
  • Org upsert by repository.owner.id (lines 140–144), then skip if org.isInstalled === false (line 147).
  • Monthly quota via checkAndResetOrgQuota(); limits free: 50, pro: 500, enterprise: 10000 (lines 8–12).
  • Repo upsert by repository.id (lines 170–180); skip if repo.enabled === false (line 190).
  • Skip synchronize when org.triggerOnSync === false (line 183).

Then creates PRReview { status: 'pending' } (line 197) and enqueues a BullMQ job whose job_id is that row's id (line 207).

In: validated webhook JSON.  Out: Organization, Repo, PRReview(pending) rows + one queued job; HTTP 200 (also on internal failure, deliberately, to stop GitHub retries).
STEP 3

Queue and worker pickup

api/src/queues/reviewQueue.ts  →  api/src/workers/reviewWorker.ts

The queue is review-queue with attempts: 3 and exponential backoff from 5 s (reviewQueue.ts:12–23). The worker is constructed at import time (reviewWorker.ts:8, imported by app.ts:16) with concurrency: 3 and a 5-minute lock. It loads the PRReview plus org; if the row is missing it skips without retry.

It then counts FeedbackAction rows for the org and computes pastDismissalRate = dismissed / total, defaulting to 0.2 when there is no history (lines 26–32).

In: job data { job_id, repo, pr_number, installation_id, head_sha }.  Out: HTTP POST ${AGENT_URL}/review via triggerReview() (api/src/services/agent.ts:6), 300 s timeout, with x-internal-secret.
STEP 4

Agent authentication and graph start

agent/app/api/routes.py → verify_internal_secret() · review_pr()

Every agent route depends on verify_internal_secret() (line 12, applied at line 37). Header x-internal-secret must equal INTERNAL_SERVICE_KEY; an unset server key returns 500, a wrong one 403. Startup validation (agent/app/core/config.py:24) hard-fails if INTERNAL_SERVICE_KEY, GROQ_API_KEY, or DATABASE_URL is missing.

review_pr() builds the initial state and calls review_graph.ainvoke({...}) (line 78).

In: { job_id, repo, pr_number, installation_id, confidence_threshold, past_dismissal_rate, head_sha }.  Out: a completed ReviewState serialized into JSON for the Node API.
STEP 5

Fetch the diff

agent/app/graph/review/nodes/fetch_pr.py → fetch_pr()  ·  agent/app/services/github.py → get_pr_details(), get_github_client()

The agent exchanges its installation id for an installation token: it calls POST ${NODE_API_URL}/internal/installation-token (agent/app/services/github.py:12–21), which lands on api/src/routes/internal.ts:9 → getInstallationOctokit() in api/src/lib/octokit.ts. That function caches in Redis under installation_token:<id> for 55 minutes (lines 31–43, 62); on a miss it signs an RS256 app JWT (generateJWT(), line 8) and calls GitHub's /app/installations/<id>/access_tokens (lines 46–56).

With the token, get_pr_details() iterates pr.get_files() and keeps {filename, patch, additions, deletions, status}; files without a patch are dropped (binary or too large), github.py:36–44.

In: repo full name, PR number, installation id.  Out: changed_files[] + head_sha.
STEP 6

Load repository custom rules

agent/app/graph/review/nodes/fetch_config.py → fetch_config()

Looks for .powerful.yml, then .powerful.yaml, at the PR head SHA (line 30). Base64-decodes the contents, runs yaml.safe_load, and accepts either { rules: [...] } or a bare YAML list (lines 36–41). A 404 is expected and ignored; malformed YAML is logged and the review proceeds with no rules.

In: repo + head_sha.  Out: custom_rules: string[] (possibly empty).
STEP 7

Chunk the diff for the LLM

agent/app/graph/review/nodes/chunk.py → chunk_changes()

Per file, walk patch lines: @@ starts a new chunk and parses the new-file start line; lines starting with +, -, or a space are kept; - lines do not advance the new-file line counter (line 37); a chunk is flushed every 30 lines (line 39).

In: changed_files[].  Out: chunks[] = { filename, content, start_line, end_line }.
STEP 8

Retrieve team memory (RAG)

agent/app/graph/review/nodes/search.py → search_memory_for_chunks()  ·  agent/app/services/memory.py → search_memory()

Each chunk is embedded with embed() (agent/app/services/embeddings.py, BAAI/bge-small-en-v1.5, 384 dimensions). SQL orders by cosine distance and returns the top 3 per chunk:

SELECT "content", "outcome", "prNumber",
       1 - ("embedding" <=> $1::vector) AS similarity
FROM "MemoryEntry"
WHERE "repoId" IN (SELECT "id" FROM "Repo" WHERE "id" = $2 OR "fullName" = $2 OR "name" = $2)
ORDER BY "embedding" <=> $1::vector
LIMIT $3

Only hits with similarity > 0.4 survive (search.py:16).

In: chunk text.  Out: chunks_with_memory[], each chunk plus up to 3 past decisions.
STEP 9

Score PR risk

agent/app/graph/review/nodes/score_risk.py → score_risk()

Four weighted buckets, clamped to 5–100 (lines 79–80): diff size 5/12/20/26/30 points for ≤50/≤200/≤500/≤1000/>1000 lines; file count 4/9/15/20 for 1–2/3–5/6–10/>10 files; criticality from filename regexes (one hit per category, capped at 35) — auth/session/security 18, payments 15, infrastructure/schema 12, core logic 8; team dismissal friction min(15, max(2, round(rate × 25))).

It immediately posts a commit status via post_commit_status() (agent/app/services/github.py:54) with context Powerful AI / PR Risk: success below 30, pending at 30–70, failure above 70.

In: changed files + dismissal rate.  Out: risk_score, risk_breakdown, and a GitHub commit status.
STEP 10

LLM review

agent/app/graph/review/nodes/llm_review.py → llm_review()  ·  agent/app/services/llm.py

One Groq call per chunk (line 28). Model: llama-3.3-70b-versatile, temperature 0.1. System message: “You are a precise code reviewer. Output only valid JSON arrays.”, plus any custom rules. The human message contains the filename, line range, raw diff, optional rules, optional memory precedents, and a strict JSON output schema.

Responses are stripped of Markdown fences, parsed with json.loads, and every issue with confidence < confidence_threshold is dropped (lines 80–82). A malformed chunk is logged and skipped — the run continues.

In: chunks + memory + rules + threshold.  Out: comments: ReviewComment[], llm_calls, prompt/completion/total tokens.
STEP 11

Post the GitHub review

agent/app/graph/review/nodes/post_comments.py → post_comments()  ·  agent/app/services/github.py → post_pull_request_review()

Event selection (post_comments.py:11–30): no comments → APPROVE with “✅ PR Review Agent — No issues found. Looks good!”; any error severity → REQUEST_CHANGES; otherwise COMMENT.

Builds a Markdown body grouped by file with severity icons (🔴 / ⚠️ / 💡), line number, comment, optional past-PR reference, and confidence (lines 32–46). Inline comments use { path, line, body } (lines 48–57). The service calls pr.create_review(commit=repo.get_commit(pr.head.sha), body=..., event=..., comments=...) with side: "RIGHT"; any exception falls back to a single create_issue_comment(body), losing inline annotations (github.py:109–138).

In: comments + PR identity.  Out: posted_urls, the GitHub review URL.
STEP 12

Notify, persist, and meter

agent/app/graph/review/nodes/notify.py → notify_complete()  ·  api/src/workers/reviewWorker.ts

The agent posts /internal/review-complete with { job_id, comments_count, comment_url, status } (line 12–22); internal.ts:26 updates the PRReview row and emits a done event. The worker then writes the detailed record: reviewComment.createMany(), PRReview completion fields, Repo.customRulesCount, a second commit status with a dashboard link, a UsageEvent, and Organization.monthlyReviewCount += 1 (lines 44–129).

On failure, worker.on('failed') marks the review failed (lines 137–147); BullMQ retries up to 3 times.

In: agent result.  Out: completed DB rows, commit status, usage event, incremented quota counter.
STEP 13

Live progress, throughout

agent/app/services/progress.py → report_progress()  ·  api/src/lib/pipelineEvents.ts → emitPipelineEvent()  ·  api/src/routes/internal.ts → handlePipelineStream()

Every node calls report_progress(job_id, node, status, message, meta), which POSTs to /internal/pipeline-update (internal.ts:63). emitPipelineEvent() publishes to pipeline:<job_id> and appends to pipeline_history:<job_id> with a 1-hour TTL. The SSE endpoint GET /api/pipeline/stream/:job_id replays history, subscribes to the channel, and heartbeats every 15 s.

In: node name, status, message, metadata.  Out: SSE data: frames to the dashboard.

4.4Make a sample PR actually trigger a review

The review path needs a real GitHub App installation: get_github_client() raises "Installation ID is required." (agent/app/services/github.py:27) even though its docstring mentions a PAT fallback. Only onboarding uses GITHUB_TOKEN (agent/app/graph/onboard/nodes/fetch_history.py:15).

  1. Create a GitHub App with callback http://localhost:3000/auth/github/callback, setup URL http://localhost:3000/auth/github/installed, and a webhook URL pointing at your tunnel.
  2. Grant permissions — Pull requests: Read & write; Issues: Read & write; Contents: Read-only; Metadata: Read-only (README.md:138–144). Subscribe to Pull request events (README.md:148).
  3. Download the private key into GITHUB_PRIVATE_KEY, keeping the \n escapes — octokit.ts:10 converts them back.
  4. Start the tunnel (README points at Smee/ngrok; smee-client is not a repo dependency): 
    npx smee-client --url https://smee.io/<your-channel> \
  --target http://localhost:3000/webhooks/github
  5. Install the App on a throwaway repo. Create a branch, edit three files (one under an auth/session path, one under billing/payment, one UI file), push, and open the PR.

4.7Faster loop — call the agent directly

Skips webhook and queue, but still needs a valid installation id and a real PR:

curl -X POST http://localhost:8000/review \
  -H "Content-Type: application/json" \
  -H "x-internal-secret: $INTERNAL_SERVICE_KEY" \
  -d '{"job_id":"manual-1","repo":"acme/shop","pr_number":482,
       "installation_id":12345678,"confidence_threshold":0.5,
       "past_dismissal_rate":0.2}'

It will post a real review to GitHub. No PRReview row exists, so /internal/review-complete is a no-op (updateMany, internal.ts:35) and comments are not persisted; SSE still works under manual-1.

Section 05Interview gotchas

Things the code does that the README does not say — useful for showing depth, and for avoiding overclaims.

5.1Seven details worth raising

  1. No PAT fallback in the review path. The docstring at agent/app/services/github.py:5–9 says it falls back to a personal token, but line 27 raises "Installation ID is required.". Only onboarding accepts GITHUB_TOKEN.
  2. Memory retrieval is repo-scoped, not org-scoped. search_memory() filters only on repoId (memory.py:90–92), while MemoryEntry stores orgId and the README claims org+repo scoping.
  3. The embedding model in the README is wrong. Code uses BAAI/bge-small-en-v1.5 (embeddings.py:4); README says all-MiniLM-L6-v2. Both are 384-dimensional.
  4. Two commit statuses per review. score_risk.py:116 posts one, then reviewWorker.ts:85 posts another with the same context; the worker's wins and adds a dashboard link.
  5. LLM line numbers are trusted. post_comments.py:51 passes them straight to GitHub. An invented line makes create_review throw, and the fallback collapses everything into one plain PR comment with no inline threads.
  6. Two writers update the same row. notify_complete (internal.ts:35) and the worker (reviewWorker.ts:60) both write PRReview; values agree, but it is duplication.
  7. No tests, no CI, no LICENSE file in the tree. Verification today is manual PRs plus log inspection; say that plainly rather than implying a test suite.

5.2Where to say “I'm not sure”

  • Why 5c39865 is called “upgraded”. The message says nothing; the content is inferred from git show --stat.
  • Whether the weekly digest is emailed. cron.ts:39 enqueues a job and digestQueue.ts exists, but I did not trace the worker to a mail provider.
  • The frontend SSE consumer. The server endpoint and handler are clear (app.ts:106, internal.ts:93); the browser component I did not open.
  • Whether docker compose exec api npx prisma db push works as written. The runtime image omits devDependencies, so verify before relying on it; the host-side fallback in 4.1 is safer.
The 30-second summary

“GitHub sends a signed webhook. The Node API verifies it, enforces org/repo/quota rules, writes a pending review row, and queues a BullMQ job. A worker enriches the job with the org's sensitivity and dismissal history, then calls a FastAPI service. A LangGraph pipeline fetches the diff, loads .powerful.yml, slices it into 30-line chunks, recalls similar past decisions from pgvector, scores risk, asks Groq's llama-3.3-70b for JSON findings per chunk, and posts a real GitHub review with inline comments. Every node streams progress through Redis to an SSE dashboard, and the result is persisted with token usage and a monthly counter.”
